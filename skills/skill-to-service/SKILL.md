# skill-to-service — 스킬을 웹 서비스 MVP로 바꾸는 결선 킷

이 킷은 **예선에서 만든 스킬 하나를 골라**, 그것을 **Vercel에 배포된 공개 웹 서비스 MVP**로 바꾸는 과정을 가이드한다.

**서비스 MVP의 정의 (이 킷에서 쓰는 기준):**
- Vercel에 배포되어 URL 하나로 접근 가능
- 계정 가입 없이, 처음 들어온 외부 사용자가 설명 없이 사용할 수 있는 형태
- 예선 스킬이 서비스의 핵심 기능(P0)을 담당

## 세 가지 모드

사용자가 어떤 말을 하느냐에 따라 진입 모드가 달라진다. 모드 감지는 user 발화 기준으로 한다.

### (A) 대화 모드

**트리거 발화 (다음 중 하나라도 포함하면 대화 모드):**
- "스킬을 서비스로 만들고 싶다"
- "결선 아이디어"
- "MVP 아이디어 구체화"
- "서비스 아이디어 대화 시작"

**동작:**
1. **스킬 건강검진(A-0)** 을 먼저 수행한다 — 아래 "A-0 스킬 건강검진" 섹션 참조.
2. 건강검진 결과 요약 후, **서비스를 위한 5 걸음**을 순서대로 진행한다. 각 걸음은 한 번에 하나씩 묻고, 사용자가 답하면 다음 걸음으로 넘어간다.
   - 걸음 1 — WHO: 누가 이 서비스를 쓰는가
   - 걸음 2 — WHEN: 어떤 시점에 쓰는가 (언제 필요해서 여는가)
   - 걸음 3 — INPUT / OUTPUT: 들어오는 것, 나가는 것
   - 걸음 4 — SETUP: 어떤 연결이 필요한가 ( Solar 호출 방식, 데이터 저장, 외부 API 등)
   - 걸음 5 — SOLVE: 핵심 처리 흐름을 한 줄로
3. 5 걸음이 끝나면 요약하고, PRD로 넘어갈지(모드 B) 구현으로 넘어갈지(모드 C) 사용자에게 묻는다.

**대화 모드 규칙:**
- 각 걸음의 질문은 한 번에 하나씩만 한다.
- 사용자의 답변을 대신 해석해서 확정되지 않은 내용을 확정하지 않는다. 애매하면 "확인 필요"로 두고 넘어간다.
- 예선 스킬을 기준으로 하되, 서비스 맥락에서 필요한 확장만 묻는다. 예선 스킬 범위를 넘는 새 기능을 임의로 만들지 않는다.

### (B) PRD 모드

**트리거 발화:**
- "PRD로 정리해줘"
- "PRD 만들어줘"
- (대화 모드 5 걸음이 끝난 뒤 PRD로 넘어가기로 한 경우 자동 진입)

**동작:**
지금까지 대화에서 수집된 실질 정보만 사용해 **미니 PRD**를 작성한다. 미니 PRD는 "Solar(에이전트)에게 주는 설계도" 역할이며, 다음 항목을 포함한다.

1. 서비스 한 줄 설명
2. 타겟(WHO)과 사용 시점(WHEN)
3. INPUT / OUTPUT
4. SETUP — Solar 호출 방식, 데이터 저장 방식, 외부 연결(있을 경우)
5. 핵심 처리 흐름(SOLVE) — 단계별
6. 예선 스킬과의 관계 — 어떤 스킬이 핵심 P0인지, 어떻게 서비스에 녹아드는지
7. 구현 범위(P0 / P1 구분) — P0는 서비스 MVP에 반드시 들어가야 하는 것, P1은 있으면 좋지만 필수는 아닌 것
8. 배포 방식 — Vercel 프론트 + 백엔드(있을 경우) 구성, 환경변수 종류
9. 미확인/확인 필요 사항 목록 — 실데이터로 확정되지 않은 항목

PRD를 출력한 뒤, 사용자에게 "이 PRD로 구현을 진행할지" 확인한다. 사용자가 승인하면 모드 C로 넘어간다.

### (C) 구현 가드 모드

**트리거 발화:**
- "구현해줘"
- "MVP 만들어줘"
- "PRD대로 만들어줘"
- (PRD 모드에서 사용자가 승인한 경우 자동 진입)

**동작:**
PRD가 이미 있을 때만 진입한다. PRD가 없으면 먼저 PRD가 필요하다고 알리고, PRD를 만들게 하거나 이미 있는 PRD를 제시하도록 요구한다.

구현 순서는 반드시 다음 순서를 지킨다.

1. **PRD 확인** — PRD 내용을 다시 요약 제시하고, 사용자에게 "이대로 진행할지" 최종 확인.
2. **구현 계획** — 무엇을 어떤 순서로 만들지 단계별 계획을 제시. 프론트/백엔드/스킬 연동/배포 순으로 정리할 것.
3. **승인** — 계획을 제시하고 사용자 승인 요청.
4. **구현** — 승인된 계획대로 코드를 작성·수정.
5. **배포** — Vercel 배포(프론트는 Vercel, 백엔드는 별도 경로가 있으면 그 경로). 환경변수 설정 포함.
6. **동작 확인** — 배포된 URL로 실제 동작 확인. 시크릿 모드 첫 접속 기준으로 통과하는지 체크.

**구현 가드 규칙:**
- PRD 범위를 넘어 임의 확장하지 않는다.
- 시크릿 모드 첫 접속 기준을 항상 확인한다.
- 구현 중 막히는 지점이 있으면 사용자에게 알리고 대안을 상의한다. 혼자 추측해서 진행하지 않는다.

## A-0 스킬 건강검진

대화 모드 진입 시 가장 먼저 수행하는 검사. 아래 항목을 점검하고 결과를 요약한다.

### 1. 스킬 정체성
- 스킬 이름과 용도 (무엇을 하는 스킬인가)
- 이 스킬이 예선에서 어떤 역할을 했는지
- 이 스킬이 서비스 MVP에서 맡을 핵심 기능(P0)은 무엇인지

### 2. 입력 형태
- 스킬이 받는 입력의 종류 (공고 PDF, 텍스트, 사용자 정보 등)
- 입력 수단: 파일 업로드인지, 텍스트 붙여넣기인지, 폼 입력인지
- 서비스에서 같은 입력을 어떻게 받을지 (웹에서 구현 가능한 입력 형태인지)

### 3. 출력 형태
- 스킬의 출력 형태 (판정 결과, 조건 대조표, 근거 등)
- 서비스에서 그 출력을 어떻게 보여줄지 (화면 구성 가능성)

### 4. 상태·저장 필요 여부
- 사용자 정보를 저장해야 하는가 (대화 맥락 유지 필요 여부)
- 한 번 쓰고 끝나는지, 여러 번 반복해서 쓰는지
- 사용자별 저장/기록이 필요한가

### 5. 외부 의존
- 웹 검색이 필요한가 (skill-to-service는 공고 기반 판정 스킬의 경우 공고는 사용자 제공만 사용한다는 원칙을 유지)
- Solar 호출 외에 다른 API/데이터가 필요한가
- 파일 처리(PDF/HWP/XLSX 등)가 필요한가 — 서비스에서 같은 처리 파이프라인을 쓸 수 있는지

### 6. 서비스화 적합도
- 계정 없이 URL로 접근 가능한 형태인가
- 시크릿 모드 첫 접속 시 바로 사용 가능한가
- 모바일에서도 쓸 수 있는가 (가로/세로 고려)

### 7. 예선 스킬 보존
- 예선 스킬의 핵심 규칙(공고에 없는 조건을 외부에서 가져오지 않는다, 웹 검색으로 보완하지 않는다, 최종 판정이 아니라 1차 확인임을 명시 등)을 서비스에서도 유지하는가
- 서비스에서 예선 스킬이 단순 호출 수준이 아니라 핵심 P0인지

### 건강검진 출력
- 각 항목별로 "확인 / 확인 필요 / 미확정" 표시
- 전체 적합도 한 줄 의견
- 확인 필요 항목 목록

## 공통 규칙

- **답을 대신 정하지 않는다.** WHO, WHEN, INPUT/OUTPUT, SETUP, SOLVE 모두 사용자가 답하거나 실데이터로확정되는 값만 쓴다. 없는 값은 "확인 필요/미확정"으로 둔다.
- **실데이터만 쓴다.** 현재 프로젝트에 실제로 존재하는 파일, 설정, 배포 상태를 근거로 말한다. 없는 설정이나 배포 상태를 있다고 말하지 않는다.
- **예선 스킬을 핵심으로 유지한다.** 서비스 MVP에서 예선 스킬이 핵심 P0이며, 단순 호출/참조에 그치지 않게 설계한다.
- **이 킷은 답을 주지 않고 질문을 정리한다.** 사용자에게 선택지를 제시하되, 최종 결정은 사용자가 한다.

## 관련 파일

- 현재 프로젝트 구조: 작업 디렉토리 루트 기준
- 프론트엔드: `frontend/`
- 백엔드: `backend/` (있을 경우)
- 배포: Vercel (프론트), 백엔드 배포처가 있으면 그 경로
