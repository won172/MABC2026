결선 OT 내용
결선 OT 스크립트를 기준으로 보면, 이번 MABC 결선의 핵심은 “예선에서 만든 개인용 Skill을 실제 사용자가 쓸 수 있는 서비스 MVP로 확장하는 것”입니다. 발표 준비 관점에서 필요한 내용만 추리면 아래처럼 정리할 수 있습니다.1. 결선의 핵심 주제예선에서는 ‘나의 문제를 해결하는 Skill’을 만들었다면, 결선에서는 이를 ‘다른 사람도 사용할 수 있는 서비스’로 확장해야 합니다.즉,나만 사용하던 Skill → 특정 사용자의 문제를 해결하는 공개 서비스 MVP로 전환하는 것이 핵심입니다.주최 측이 강조하는 MVP는 단순히 기능을 많이 구현하는 것이 아니라 최소한의 핵심 기능으로 실제 문제를 해결할 수 있는 제품입니다.따라서 서비스 기획에서 특히 중요한 질문은 다음 5가지입니다.구분

MVP 범위 설정 원칙교육에서 상당히 강하게 강조한 개념이 있습니다.“있으면 좋은 기능”과 “없으면 서비스가 성립하지 않는 기능”을 구분하라.예를 들어 약물 알레르기 서비스의 경우핵심 MVP는알레르기 성분 입력 → 약 이름 입력 → 성분 확인 → 위험 여부 + 근거 제공입니다.반면사진 OCR, 음식 알레르기 지원, 과거 검색 기록, 추천 기능 등은 추후 기능입니다.즉 결선에서는 기능을 많이 넣는 것보다핵심 사용자 문제 하나를 완결성 있게 해결하는 것이 더 중요합니다.10. Hermes를 사용하면Hermes는 훨씬 자유도가 높습니다.Skill을 업로드한 뒤 마찬가지로Skill 검증→ 서비스 인터뷰→ PRD→ 구현→ GitHub→ Vercel방식으로 진행합니다.추가적으로 GitHub, Vercel 등의 MCP를 붙여 개발·배포까지 Agent에게 진행시킬 수 있습니다.다만 교육에서 계속 강조한 부분은“Agent가 했다고 말하는 것을 그대로 믿지 말고 실제로 확인하라.”입니다.예를 들어 Agent가배포 완료라고 답하더라도 직접 URL에 접속해서입력 → 버튼 → API 호출 → 결과전체 Flow를 반드시 테스트해야 합니다.14. 멘토링 활용법팀별 담당 멘토가 배정되고 30분 × 2회 멘토링을 받을 수 있습니다.주최 측 권장 방식은초반에는 기획/MVP,후반에는 개발/디버깅입니다.멘토링에 대해서도 중요한 조언이 있었습니다.멘토에게 “뭘 만들면 좋을까요?”라고 묻기보다 현재 기획안, 문제점, 선택지를 정리해서 논의하라는 것입니다.즉,A와 B 중 어느 방향이 평가 기준상 더 적절한가?P0 기능을 이 3개로 잡았는데 과한가?현재 이 Flow에서 사용성이 떨어지는데 어떤 방식이 나은가?처럼 질문하는 것이 좋습니다.15. 이 OT 전체를 한 문장으로 정리하면결선의 핵심은 “기술적으로 화려한 서비스를 만드는 것”이 아니라, 예선 Skill을 중심으로 특정 사용자의 명확한 문제를 해결하는 작동 가능한 MVP를 만드는 것입니다.따라서 기획할 때는 아래 흐름이 가장 중요합니다.Target User → Pain Point → Use Moment → Skill → Core Function → Output → User Value예를 들어:사회초년생 → 첫 월세 계약이 불안함 → 계약 전날 → 계약 위험조항 검출 Skill → 계약서 분석 → 위험조항 + 질문 리스트 → 계약 전 확인해야 할 내용을 빠르게 파악이 정도로 연결되어야 합니다.PM 관점에서 보면 가장 중요한 5가지타겟을 최대한 좁힌다.사용 순간(When)을 명확히 만든다.예선 Skill을 서비스의 핵심 P0 기능으로 만든다.P1 기능을 과감히 버리고 End-to-End 동작을 완성한다.발표에서는 기능 설명보다 ‘사용 전 → 사용 후 변화’를 보여준다.특히 MABC 결선은 기획력 25점 + 창의성 20점 + Skill 활용도 높은 배점 구조이기 때문에, 단순한 개발 완성도보다 “왜 이 서비스여야 하는가”를 논리적으로 설계하는 것이 상당히 중요해 보입니다.원하시면 다음 단계로는 지금 준비하고 있는 우리 MABC 아이디어를 이 평가 기준에 대입해서, ‘현재 기획에서 점수를 더 받을 수 있는 부분 / 버려야 할 기능 / 발표에서 강조해야 할 포인트’까지 심사위원 관점으로 분석해드릴 수 있습니다.
