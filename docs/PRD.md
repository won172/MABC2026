## 0. OT에서 강조된 5가지 정의 (먼저 확정)

주최 측이 MVP 범위를 정하기 위해 반드시 답해야 한다고 강조한 5가지 질문. 이 답변이 PRD 전체의 기준이다.

| 구분 | 우리 답변 (초안, 논의 필요) |
|------|---------------------------|
| **Who (누가)** | 청년주택 공고를 혼자 보고 있는 **첫 신청 준비 중인 청년**. 특히 "공고 PDF를 열었는데 용어가 어렵고, 내 조건이 되는지 하나씩 확인하기 부담스러운 사람" |
| **When (언제/어떤 상황)** | 공고를 발견한 직후, 신청 전에 **"내가 이거 신청 가능해?"**를 빠르게 확인하고 싶은 순간. 여러 번 반복해서 다른 공고도 확인하고 싶음 |
| **Input / Output** | Input: ① 사용자 기본 정보(온보딩) ② 공고(PDF/텍스트 업로드 또는 API 공고 선택). Output: 🟢/🔴/🟡 최종 판정 + 항목별 대조표(⭕/❌/⚠️) + 근거 + 신청 전 확인할 것 + 시행기관 심사 안내 |
| **Setup (설정/외부 연결)** | Solar Pro 4 API + youth-housing-eligibility-checker 스킬 프롬프트. 공고 입력을 위해 (선택) 공공데이터포털 LH 공고 API. 파일 파싱을 위해 PDF/HWP/텍스트 파서. 배포는 Vercel. Hermes 플랫폼 사용 시 MCP로 GitHub/Vercel 연동 가능 |
| **Solve (어떤 문제 해결)** | "공고문을 내가 직접 읽고 내 조건과 1:1 대조하는 시간과 부담을 줄인다. 불확실한 부분은 무엇을 확인해야 하는지까지 안내받는다." |

> 위 5개 답이 흔들리면 기능 범위가 흔들린다. 팀 논의로 확정 필요.

## 1. 서비스 개요

### 1.1 한 줄 요약
사용자가 본인 정보를 한 번 입력하면, 청년주택 모집공고(PDF/텍스트 업로드 또는 API 공고 선택)를 보고 채팅 방식으로 **"이 공고 내가 신청할 수 있어?"**를 **실시간으로 판정**받는 웹 서비스. 판정은 항목별 대조표(⭕/❌/⚠️)와 근거, 확인 필요 사항까지 함께 제공.

### 1.2 서비스 이름 (가안, 논의 필요)
- **청년주택 자격체크** / **청집체크** / **청년주택 EligibilityChecker**
- (팀 내 협의로 오늘 중 확정 권장)

### 1.3 핵심 가치
- 공고 PDF를 직접 읽지 않아도 됨 (AI가 구조화해 내 조건과 1:1 대조)
- 채팅하듯 "이 공고 신청해?" → 1분 내로 판정 + 근거
- 판정 결과를 ⭕/❌/⚠️ 대조표와 함께 제공해 신뢰도 확보
- **예선 당선 Skill(youth-housing-eligibility-checker)이 이 서비스의 핵심 P0 기능**

### 1.4 대상 사용자 (OT 권장: 타겟 좁히기)
- **1차 타겟 (MVP)**: 청년주택 공고를 처음 준비하면서 혼자 자격 판단이 부담스러운 청년. "공고 PDF를 열어봤는데, 내 소득/자산/거주조건이 되는지 하나씩 확인하기 어렵다"는 사람
- **넓은 타겟 (참고)**: 청년주택 신청을 고려하는 청년 전반 — 마케팅/확장 단계에서 고려, MVP 타겟으로는 너무 넓음

> OT 메시지: "2030 사회초년생"보다 "첫 월세 계약을 앞두고 계약서를 혼자 검토해야 하는 2030 사회초년생"이 훨씬 강한 타겟. 우리도 공고 문맥을 더 구체화할수록 좋음.

## 2. 기획 의도 및 배경

### 2.1 문제 정의
- 청년주택 모집공고는 PDF/HWP 형태로 게시되며, 자격조건이 여러 섹션에 흩어져 있음
- 소득·자산·자동차 가액 산정 기준이 복잡해 사용자가 스스로 판단하기 어려움
- 공고가 여러 개 올라오면 각각 직접 대조해야 해서 시간이 많이 듦
- 공고 용어(신청계층, 기준시점, AND/OR 조건, Tier별 조건 등)를 오해하면 자격 판단 자체가 틀어짐

### 2.2 해결 방안 (Skill → 서비스)
- **공고 입력**: 최신 공고를 API로 불러오거나, 사용자가 PDF/텍스트를 업로드 → AI가 자격조건을 추출·구조화
- **대화형 자격 판정**: 사용자 정보를 한 번 입력받고, 채팅으로 "이 공고 신청해?" → AI가 공고 조건과 1:1 대조해 판정 (Skill의 10단계 흐름을 그대로 서비스로)
- **근거 제시**: 항목별 대조표(⭕/❌/⚠️) + 판단 근거 + 신청 전 확인할 것 + 시행기관 심사 안내

### 2.3 예선 스킬과의 관계 (중요 — 평가 배점 30점: 예선 Skill 활용도)
- 이 서비스의 **핵심 P0 기능은 youth-housing-eligibility-checker 스킬 그 자체**
- Skill이 단순히 내부에서 호출되는 정도가 아니라, **이 Skill이 없으면 서비스 핵심 가치가 없어지는 수준**으로 설계
- Skill 내용(SKM.md 10단계 흐름, 5개 핵심 원칙)은 서비스에 그대로 적용. 서비스 맥락에 맞춰 수정/확장은 허용
- **예선 당선 Skill이 서비스 MVP의 핵심 기능을 담당해야 함** (OT 규정)

## 3. MVP 범위: P0 / P1 구분

OT에서 강조한 대로 **"없으면 서비스 성립 안 되는 기능(P0)"**과 **"있으면 좋지만 없어도 되는 기능(P1)"**을 명확히 구분. 결선 기간이 짧으므로 P0 완성도 우선.

> 약물 알레르기 서비스 예시 (OT): 핵심 MVP = 알레르기 성분 입력 → 약 이름 입력 → 성분 확인 → 위험 여부 + 근거 제공. 사진 OCR, 음식 알레르기, 검색 기록, 추천은 추후 기능.

### 3.1 P0 — MVP를 성립시키는 필수 핵심 기능

#### P0-1. 사용자 정보 등록/수정 (온보딩)
- 나이/생년월일, 거주지역/거주기간, 혼인 여부, 가구 구성, 취업 상태, 월평균 소득(모름 가능), 총자산(모름 가능), 자동차 보유/가액(모름 가능), 무주택 여부
- 저장/수정
- "모름" 옵션 제공 → 모든 항목을 강제하지 않음 (스킬 원칙: 공고가 요구하는 항목만)

#### P0-2. 공고 입력 (최소 1개 채널)
- **1순위**: 파일 업로드(PDF/텍스트) 또는 텍스트 붙여넣기 — API와 무관하게 항상 작동해야 함 (API 미연동/실패 시에도 서비스 성립)
- **2순위(선택)**: API 공고 목록/선택 — 있으면 편리하지만 P0 서비스의 필수 조건은 아님 (P1으로 두거나, API 연동 성공 시에만 활성화)
- 이유: "공고 API 없이도, 사용자가 PDF/텍스트를 업로드하면 판정이 되어야 서비스 성립"

#### P0-3. 공고 파서 → 자격조건 구조화
- 업로드/붙여넣은 공고에서 핵심 자격조건 추출 (나이, 거주지역, 소득, 자산, 무주택, 신청계층, 가구 구성, 혼인 조건 등)
- 필수조건 vs 우선순위/가점 조건 구분
- 기준시점 확인
- 신청계층 중첩 시 처리
- 추출 결과를 오른쪽 정보 영역에 표시

#### P0-4. 채팅 인터페이스 (자격 판정) — Skill의 핵심 실행
- AI 에이전트가 대화 형식으로 자격 판정 수행 (Solar Pro 4 + Skill 프롬프트)
- 저장된 사용자 정보 + 공고 자격조건 + 추가 질문으로 1:1 대조
- 정보 부족하면 ⚠️ 확인 필요로 표시하고 무엇을 추가로 확인해야 하는지 질문
- 판정 결과: 🟢/🔴/🟡 + 항목별 대조표(⭕/❌/⚠️) + 판단 근거 + 신청 전 확인할 것 + 시행기관 심사 안내

#### P0-5. 오른쪽 정보 표시 (현재 맥락 공고 + 대조 미리보기 + 판정 결과)
- 현재 채팅 맥락의 공고 정보 (공고명, 공고일, 마감일, 유형, 출처 링크)
- 공고 자격조건 요약 카드
- 내 정보 vs 공고 조건 대조 미리보기
- 판정 완료 시 결과 카드

#### P0-6. 스킬 원칙 준수 (규정)
- 공고에 없는 조건을 외부에서 가져오지 않음
- 웹 검색으로 공고 내용을 보완하지 않음
- 소득·자산·자동차 가액은 AI가 대신 계산/조회하지 않음 (사용자 직접 확인 경로 안내)
- 확실하지 않으면 "신청 가능"으로 확정하지 않음 (⚠️ 확인 필요)
- 판정 결과 하단에 시행기관 심사 안내 문구 포함

### 3.2 P1 — 있으면 좋지만 없어도 서비스 성립 (결선 기간엔 버리거나 최소 구현)

#### P1-1. 공고 API 연동 (공고 목록/선택)
- 공공데이터포털 LH 분양임대공고 API / 마이홈포털 API 등
- API 연동 성공 시 오른쪽/하단에 최근 공고 리스트 표시
- **미연동 시에도 파일 업로드/텍스트 입력으로 서비스 작동해야 함**

#### P1-2. 판정 히스토리
- 이전 판정 기록 저장/조회
- P0 판정 흐름 자체에는 영향 없음

#### P1-3. 공고 비교 기능
- 여러 공고를 나란히 비교
- youth-housing-compare 스킬과 연계 가능하지만, 현재 예선 당선 Skill은 eligibility-checker이므로 MVP 핵심 아님

#### P1-4. 알림/모니터링
- 관심 지역/조건 설정 시 신규 공고 알림
- MVP 범위 밖

#### P1-5. 모바일 반응형
- 데스크톱 분할 화면을 기본으로 하고, 모바일 대응은 P1 또는 발표 데모 환경 우선 대응

## 4. 사용자 시나리오 (End-to-End, P0 기준)

### 4.1 첫 방문 → 본인 정보 입력 (온보딩)

1. 사용자가 서비스에 처음 접속
2. 환영 화면 + "본인 정보를 한 번 입력하면, 앞으로는 공고만 올리면 바로 판정받을 수 있어요" 안내
3. 기본 정보 입력 폼 (P0-1 항목)
4. "모름"은 건너뛰기 가능, "모든 정보가 필수는 아니며 공고마다 필요한 항목만 사용됨" 안내
5. 저장 후 메인 화면으로 이동

> 변동 가능 정보(취업 상태, 소득 등)는 필요 시 채팅 중 재확인. 한 번 저장했다고 해서 모든 판정에 충분하다고 가정하지 않음.

2. 사용자가 공고 텍스트 붙여넣기
3. AI가 공고 분석 → 오른쪽 자격조건 요약 카드 표시
4. 왼쪽 채팅: "이 공고의 자격조건을 확인했어요. 신청 가능 여부를 확인해드릴게요. 필요한 정보가 더 있으면 물어볼게요."
5. 저장된 사용자 정보로 확인 가능한 항목부터 대조, 부족한 정보는 질문
6. 판정 완료 → 오른쪽 결과 카드 + 채팅에 판정 메시지

**예시 B: PDF 업로드**
1. 왼쪽 업로드 버튼으로 공고 PDF 업로드
2. 파싱 → 오른쪽 자격조건 요약 카드
3. 이후 흐름은 예시 A와 동일

**예시 C: API 공고 선택 (연동된 경우)**
1. 하단/오른쪽에 최근 공고 리스트 표시 (API 연동 시)
2. 공고 클릭 → 오른쪽 공고 상세 + 왼쪽 채팅 컨텍스트 설정
3. 이후 판정 흐름 동일

### 4.4 채팅에서 AI가 하지 않는 것 (규정/원칙)
- 공고에 없는 조건을 외부에서 가져오지 않음
- 웹 검색으로 공고 내용 보완하지 않음
- 소득·자산·자동차 가액을 AI가 대신 계산/조회하지 않음
- "신청 가능" 확정은 모든 필수조건 충족 + 정보 확인 완료 시에만
- 불확실하면 ⚠️ 확인 필요 + 무엇을 확인해야 하는지 안내
- 판정 결과 하단에 시행기관 심사 안내 문구

3. 법적 최종 입주자격 확정이 아님 — 시행기관 심사로 최종 결정됨을 항상 명시
4. 확실하지 않으면 "신청 가능"으로 확정하지 않는다 (⚠️ 확인 필요)
5. 소득·자산·자동차 가액은 사용자가 직접 확인하는 경로를 안내할 뿐, 스킬이 대신 계산/조회하지 않는다

## 부록 C. Skill 동작 흐름 (10단계 → 서비스 매핑)

1. 공고 읽기 & 자료 형태 확인 → 공고 입력 채널
2. 자격조건 구조화·추출 → 공고 파서
3. 필요한 사용자 정보 파악 & 기존 정보 재사용 → 온보딩 + 채팅 중 추가 질문
4. 부족한 정보만 질문 → 채팅에서 AI가 질문
5. 각 필수조건 1:1 대조 (⭕/❌/⚠️) → 판정 로직
6. 최종 판정 (🟢/🔴/🟡) → 채팅 + 오른쪽 결과 카드
7. 신청기간과 자격조건 구분 → 판정 결과 출력에 반영
8. 공고자료 처리 오류 & 정정공고 처리 → 파서 에러 처리/UX 안내
9. 출력 형식 (판정 → 대조표 → 근거 → 신청 전 확인할 것 → 심사 안내) → 채팅 + 오른쪽 카드
10. 답변 전 품질검사 (내부 체크리스트) → AI 에이전트 내부 로직
