## 0. OT에서 강조된 5가지 정의 (먼저 확정)

주최 측이 MVP 범위를 정하기 위해 반드시 답해야 한다고 강조한 5가지 질문. 이 답변이 PRD 전체의 기준이다.

| 구분 | 우리 답변 (초안, 팀 논의 필요) |
|------|---------------------------|
| **Who (누가)** | 청년주택 공고를 직접 하나씩 확인·대조하기 부담스러운 청년. 특히 "공고가 여러 개 뜨는데 내 조건으로 신청 가능한지 빠르게 알고 싶은 사람" |
| **When (언제/어떤 상황)** | 공고를 찾거나 여러 공고를 비교할 때, **내 조건으로 신청 가능한 청년주택을 빠르게 알고 싶은 순간**. 먼저 자격요건에 맞는 공고를 찾고, 필요하면 개별 공고를 더 자세히 확인 |
| **Input / Output** | Input: ① 사용자 기본 정보(온보딩) ② 공고 데이터(API로 수집한 공고 목록/상세). Output: 1차) 본인 자격에 맞는 청년주택 추천 목록, 2차) 개별 공고 상세 판정(🟢/🔴/🟡 + 항목별 대조표 + 근거 + 확인 필요 사항 + 시행기관 심사 안내) |
| **Setup (설정/외부 연결)** | Solar Pro 4 API + youth-housing-eligibility-checker 스킬 프롬프트. 공고 데이터를 위해 (선택) 공공데이터포털 LH 공고 API 등 외부 공고 API. 판정 결과/공고 데이터 저장을 위한 데이터베이스. 채팅·추천 UI. 배포는 Vercel. Hermes 사용 시 MCP로 GitHub/Vercel 연동 가능 |
| **Solve (어떤 문제 해결)** | "여러 공고를 하나씩 열어 내 조건과 대조하는 부담을 줄이고, 내 자격에 맞는 청년주택을 먼저 추려준다. 관심 공고는 자세히 판정받아 무엇을 확인해야 하는지도 안내받는다." |

> 위 5개 답이 흔들리면 기능 범위가 흔들린다. 팀 논의로 확정 필요.

## 1. 서비스 개요

### 1.1 한 줄 요약
API로 청년주택 공고 데이터를 가져와 공고별로 자격조건을 자세히 판정하고 데이터베이스에 저장해 둔 뒤, 사용자가 본인 자격요건을 입력하고 채팅창에서 물어보면 **본인 자격에 해당하는 청년주택을 먼저 추천**하는 서비스. 이후 채팅 + 오른쪽 화면에서 지도·목록 등 실시간 정보 표시로 확장하는 것을 목표로 한다.

### 1.2 서비스 이름 (가안, 팀 협의 필요)
- **청년주택 자격체크** / **청집체크** / **청년주택 EligibilityChecker**
- (팀 내 협의로 오늘 중 확정 권장)

### 1.3 핵심 가치
- 공고를 하나씩 열어 내 조건과 대조하는 대신, **내 조건에 맞는 청년주택을 먼저 추천**받음
- 관심 공고는 **자격요건을 자세히 판정**받고, 근거·확인 필요 사항까지 함께 확인
- 판정 결과와 공고 정보를 저장해 두고, 이후 채팅 기반으로 다시 확인·추천받을 수 있음
- **예선 당선 Skill(youth-housing-eligibility-checker)이 이 서비스의 핵심 P0 기능**

### 1.4 대상 사용자 (OT 권장: 타겟 좁히기)
- **1차 타겟 (MVP)**: 청년주택 공고를 여러 개 보면서 내 조건으로 가능한지 빠르게 확인하고 싶은 청년. "공고 찾는 것부터 대조까지 혼자 하기 부담스럽다"는 사람
- **넓은 타겟 (참고)**: 청년주택 신청을 고려하는 청년 전반 — 확장 단계에서 고려, MVP 타겟으로는 너무 넓음

> OT 메시지: "2030 사회초년생"보다 "첫 월세 계약을 앞두고 계약서를 혼자 검토해야 하는 2030 사회초년생"이 훨씬 강한 타겟. 우리도 사용 순간을 더 구체화할수록 좋음.

## 2. 기획 의도 및 배경

### 2.1 문제 정의
- 청년주택 모집공고는 여러 곳에 산재하고, 자격조건이 여러 섹션에 흩어져 있음
- 소득·자산·자동차 가액 산정 기준이 복잡해 사용자가 스스로 판단하기 어려움
- 공고가 여러 개면 각각 직접 대조해야 해서 시간이 많이 듦
- 공고 용어(신청계층, 기준시점, AND/OR 조건, Tier별 조건 등)를 오해하면 자격 판단 자체가 틀어짐

### 2.2 해결 방안 (팀이 생각하는 우선순위 반영)
- **1순위: 공고 데이터 수집 → 상세 자격 판정 → 저장**
  - API 등으로 청년주택 공고 데이터를 가져온다
  - 가져온 공고별로 자격요건을 자세히 판정(공고 파서 + 자격 대조)한다
  - 판정 결과와 공고 정보를 데이터베이스에 저장한다
- **2순위: 사용자 온보딩 + 채팅 기반 추천**
  - 사용자가 본인 자격 요건(연령, 소득, 자산, 무주택, 거주지역, 가구 구성, 혼인 여부, 취업 상태, 자동차 등)을 입력한다
  - 채팅창에서 "청년주택 알려줘", "나 신청 가능한 거 있어?"처럼 물어보면, 저장된 공고 중 **본인 자격에 해당하는 청년주택을 추천**한다
- **3순위: 실시간 정보 표시 확장 (채팅 + 오른쪽 화면)**
  - 채팅창과 오른쪽에 실시간 상황을 보여주는 화면을 만든다
  - 예: 지도 위에 아파트(공고) 위치를 띄우면서 내용을 보여주기, 목록 형식으로 추천하기 등

### 2.3 예선 스킬과의 관계 (중요 — 평가 배점 30점: 예선 Skill 활용도)
- 이 서비스의 **핵심 P0 기능은 youth-housing-eligibility-checker 스킬 그 자체**
- 특히 **공고별 자격요건 상세 판정 단계**에서 스킬의 판정 로직(10단계 흐름, 5개 핵심 원칙)이 핵심 역할을 해야 함
- Skill이 단순히 내부에서 호출되는 정도가 아니라, **이 Skill이 없으면 서비스의 핵심 가치(공고 판정·추천)가 없어지는 수준**으로 설계
- Skill 내용(SKM.md 10단계 흐름, 5개 핵심 원칙)은 서비스에 그대로 적용. 서비스 맥락에 맞춰 수정/확장은 허용
- **예선 당선 Skill이 서비스 MVP의 핵심 기능을 담당해야 함** (OT 규정)

## 3. MVP 범위: P0 / P1 구분

OT에서 강조한 대로 **"없으면 서비스 성립 안 되는 기능(P0)"**과 **"있으면 좋지만 없어도 되는 기능(P1)"**을 명확히 구분. 결선 기간이 짧으므로 P0 완성도 우선.

> 약물 알레르기 서비스 예시 (OT): 핵심 MVP = 알레르기 성분 입력 → 약 이름 입력 → 성분 확인 → 위험 여부 + 근거 제공. 사진 OCR, 음식 알레르기, 검색 기록, 추천은 추후 기능.

### 3.1 P0 — MVP를 성립시키는 필수 핵심 기능

#### P0-1. 공고 데이터 수집 (API 또는 최소 1개 공고 확보 경로)
- 공공데이터포털 LH 분양임대공고 API, 마이홈포털 API 등 외부 공고 데이터를 활용해 청년주택 공고 데이터를 가져온다
- API 연동이 안 되거나 제한적인 경우에도, **적어도 서비스 시연이 가능한 수준의 공고 데이터는 확보**해야 한다 (수동 확보 데이터, 샘플 공고 데이터셋 등 포함)
- 이유: 이 서비스는 "공고 데이터를 가져와서 판정·저장·추천하는 것"이 핵심이므로, 공고 데이터 확보 자체가 P0

#### P0-2. 공고별 자격요건 상세 판정 (스킬 핵심 실행)
- 가져온 공고별로 자격조건을 추출·구조화하고, 공고 기준 자격요건을 자세히 판정한다
- 공고 파서: 공고 텍스트/파일에서 핵심 자격조건 추출 (나이, 거주지역, 소득, 자산, 무주택, 신청계층, 가구 구성, 혼인 조건, 기준시점, Tier별 조건 등)
- 필수조건 vs 우선순위/가점 조건 구분
- 기준시점 확인
- 신청계층 중첩 시 처리
- 판정 결과는 이후 DB 저장 및 추천의 기준이 된다

#### P0-3. 데이터베이스 저장
- 공고 데이터(공고명, 공고일, 마감일, 공고 유형, 주소/위치 정보, 자격조건, 출처 링크 등)를 저장
- 공고별 판정 결과(자격조건 대조 정보, 판정 관련 메타데이터 등)를 저장
- 저장 구조는 이후 "사용자 자격에 맞는 공고 추천"에 바로 활용될 수 있어야 함

#### P0-4. 사용자 정보 등록/수정 (온보딩)
- 나이/생년월일, 거주지역/거주기간, 혼인 여부, 가구 구성, 취업 상태, 월평균 소득(모름 가능), 총자산(모름 가능), 자동차 보유/가액(모름 가능), 무주택 여부
- 저장/수정
- "모름" 옵션 제공 → 모든 항목을 강제하지 않음 (스킬 원칙: 공고가 요구하는 항목만)

#### P0-5. 채팅 인터페이스 — "본인 자격에 맞는 청년주택 추천" + 필요 시 개별 공고 상세 판정
- AI 에이전트가 대화 형식으로 사용자 질문에 응답 (Solar Pro 4 + Skill 프롬프트)
- 사용자가 "청년주택 알려줘", "나 신청 가능한 거 있어?"처럼 물어보면, DB에 저장된 공고 중 본인 자격에 해당하는 청년주택을 추천
- 필요 시 특정 공고를 지정해 "이 공고 내가 신청 가능해?"라고 물어보면, 공고별로 자격 대조 후 🟢/🔴/🟡 판정 + 항목별 대조표(⭕/❌/⚠️) + 판단 근거 + 신청 전 확인할 것 + 시행기관 심사 안내
- 정보가 부족하면 ⚠️ 확인 필요로 표시하고 무엇을 추가로 확인해야 하는지 질문

#### P0-6. 추천 결과 표시 (채팅 기반 우선)
- 본인 자격에 맞는 청년주택 추천 목록을 채팅 기반으로 보여준다
- 추천 시 근거/주의사항 포함 (예: 일부 조건 확인 필요, 자격 확정 전 안내 등)
- 이 단계에서 오른쪽 실시간 UI(지도/목록형 표시)는 필수는 아니며, 채팅 기반 추천만으로도 서비스 핵심은 성립

#### P0-7. 스킬 원칙 준수 (규정)
- 공고에 없는 조건을 외부에서 가져오지 않음
- 웹 검색으로 공고 내용을 보완하지 않음
- 소득·자산·자동차 가액은 AI가 대신 계산/조회하지 않음 (사용자 직접 확인 경로 안내)
- 확실하지 않으면 "신청 가능"으로 확정하지 않음 (⚠️ 확인 필요)
- 판정 결과 하단에 시행기관 심사 안내 문구 포함

### 3.2 P1 — 있으면 좋지만 없어도 서비스 성립 (결선 기간엔 버리거나 최소 구현)

#### P1-1. 오른쪽 실시간 정보 표시 UI (지도/목록형 등)
- 채팅 + 오른쪽에 지도 위 위치 표시, 목록형 추천 등 실시간 상황 표시
- 팀이 목표로 하는 화면이나, P0 서비스 핵심은 채팅 기반 추천/판정으로 성립 가능
- MVP 시점에 어디까지 구현할지 팀 결정 필요 (예: 목록형 추천은 P0-adjacent, 지도 표시는 P1)

#### P1-2. 공고 비교 기능
- 여러 공고를 나란히 비교
- youth-housing-compare 스킬과 연계 가능하지만, 현재 예선 당선 Skill은 eligibility-checker이므로 MVP 핵심 아님

#### P1-3. 판정 히스토리 / 관심 공고 저장
- 이전 판정 기록, 관심 공고 저장/조회
- P0 추천/판정 흐름 자체에는 영향 없음

#### P1-4. 알림/모니터링
- 관심 지역/조건 설정 시 신규 공고 알림
- MVP 범위 밖

#### P1-5. 모바일 반응형
- 데스크톱 중심 화면이 기본. 모바일 대응은 P1 또는 발표 데모 환경 우선 대응

## 4. 사용자 시나리오 (End-to-End, 팀 우선순위 기준)

### 4.1 1단계: 공고 데이터 확보 → 공고별 자격 판정 → 저장 (서비스 뒷단/핵심)

**시나리오**:
1. 서비스 운영 주체(또는 서비스)가 API 등을 통해 청년주택 공고 데이터를 가져온다
2. 가져온 공고 데이터를 기반으로 공고별 자격요건을 자세히 판정한다 (공고 파서 + 자격 대조)
3. 공고 정보와 판정 결과를 데이터베이스에 저장한다
4. 이후 사용자가 조회할 때, 이미 판정된 결과를 기반으로 빠르게 응답할 수 있다

> 이 단계는 사용자-facing 시나리오와 분리되어 있지만, 서비스의 핵심 기반이다.OT 기준에서도 "공고 데이터를 가져와 판정·저장"하는 구조가 서비스의 실질 가치를 만든다.

### 4.2 2단계: 사용자 온보딩 → 채팅으로 본인 자격에 맞는 청년주택 추천

**시나리오**:
1. 사용자가 서비스에 접속
2. 첫 방문이면 본인 정보 입력(온보딩) 안내
3. 본인 자격 요건 입력/저장
4. 채팅창에서 "청년주택 알려줘", "나 신청 가능한 거 있어?"처럼 질문
5. AI가 DB에 저장된 공고 중 본인 자격에 해당하는 청년주택을 추천
6. 필요 시 특정 공고를 지목해 "이 공고 내가 신청 가능해?" 질문 → 개별 공고 상세 판정

### 4.3 3단계: 채팅 + 오른쪽 실시간 정보 표시 (확장 목표)

**시나리오**:
1. 추천/판정 결과를 채팅으로 확인하는 동시에, 오른쪽 화면에서 실시간 정보를 본다
2. 예: 추천된 공고/주택을 지도 위 위치로 표시, 목록 형식으로 추천, 선택한 공고의 상세 정보를 실시간 표시
3. 사용자가 채팅에서 다른 공고를 묻거나 필터링하면 오른쪽 화면도 함께 업데이트

### 5.3 상태 설계 (P0 기준)

- 사용자 정보 부족: "현재 정보로는 추천이 어려워요. 아래 정보를 추가로 알려주세요" + 필요한 항목만 질문
- 개별 공고 판정 불가: "이 공고는 자격조건을 충분히 확인하기 어려워요. 원문을 다시 확인하거나 다른 공고를 추천드릴게요"

## 9. 오픈 이슈 / 결정이 필요한 사항

### O1. 플랫폼 선택 (Hermes vs TimeLi) — 오늘 중 결정 권장
- **Hermes**: 자유도 높음, 개발·설정 자유도, GitHub/Vercel MCP 연동 가능. 개발 경험자에게 유리. 단 상대적으로 어려움.
- **TimeLi**: 난이도 낮음, 자연어 중심, Skill-to-Service Skill 제공, 빠른 MVP. 비개발자 친화.
- OT 정리: "빠르고 안정적으로 만들고 싶으면 TimeLi, 개발 자유도를 확보하고 싶으면 Hermes."
- 우리 팀은 개발 경험이 있으므로 Hermes 방향도 가능하지만, 9/16 마감 고려한 속도도 중요. **오늘 중 결정 필요**

### O2. 공고 데이터 확보 방식 (API vs 샘플/수동 데이터)
- 공공데이터포털 LH 분양임대공고 API, 마이홈포털 API 등 실제 API 연동 가능성 확인 필요
- API 연동이 어렵거나 지연될 경우, **시연이 가능한 수준의 공고 데이터(샘플/수동 확보 데이터)를 먼저 확보**해 서비스 핵심 흐름을 작동시키는 방향이 안전
- 이 부분이 P0 안정성과 직결됨

### O3. 공고별 자격 판정 자동화 수준
- 공고 파서 + 자격 대조 자동화의 정확도/범위
- 파서 실패 시 사용자에게 원문 재확인을 요청하는 UX 필요
- 자동 판정이 어려운 공고는 "확인 필요"로 두고, 사람이 보강할 수 있는 구조도 검토

### O4. 추천 로직의 기준
- DB에 저장된 공고 중 "본인 자격에 해당하는 청년주택"을 어떤 기준으로 추천할지 (완전 자동 판정 기준 vs 일부 확인 필요 포함 vs 우선 추천/제외 기준)
- 추천 결과의 신뢰도와 설명 가능성(왜 추천했는지)을 어떻게 보여줄지

### O5. 오른쪽 실시간 정보 표시 범위 (지도/목록형)
- 팀이 목표로 하는 "채팅 + 오른쪽 실시간 상황 표시"를 MVP에서 어디까지 구현할지
- 예: 목록형 추천은 P0-adjacent, 지도 위 위치 표시는 P1로 두는 등 단계화 검토

## 부록 A. OT 5가지 질문 요약 (PRD 기준선)

- **Who**: 청년주택 공고를 하나씩 대조하기 부담스러운 청년. 여러 공고 중 내 조건으로 가능한 걸 빨리 알고 싶은 사람
- **When**: 공고를 찾거나 비교할 때, 내 자격에 맞는 청년주택을 빠르게 알고 싶은 순간 + 관심 공고를 자세히 판정받고 싶은 순간
- **Input/Output**: Input = 사용자 기본 정보 + 공고 데이터(API/저장 데이터). Output = 1차) 본인 자격에 맞는 청년주택 추천, 2차) 개별 공고 상세 판정(🟢/🔴/🟡 + 대조표 + 근거 + 확인 필요 사항 + 심사 안내)
- **Setup**: Solar Pro 4 + youth-housing-eligibility-checker 스킬 + 공고 데이터(API/저장) + 데이터베이스 + 채팅/추천 UI + (선택) 지도/목록형 오른쪽 화면
- **Solve**: 공고를 하나씩 대조하는 부담을 줄이고, 내 조건에 맞는 청년주택을 먼저 추천받으며, 관심 공고는 자세히 판정받아 확인 필요 사항까지 안내받음

## 부록 B. 예선 당선 Skill 핵심 원칙 (서비스에도 그대로 적용)

1. 공고에 없는 조건을 외부에서 가져오지 않는다
2. 웹 검색으로 공고 내용을 보완하지 않는다
3. 법적 최종 입주자격 확정이 아님 — 시행기관 심사로 최종 결정된다는 점을 항상 명시
4. 확실하지 않으면 "신청 가능"으로 확정하지 않는다 (⚠️ 확인 필요)
5. 소득·자산·자동차 가액은 사용자가 직접 확인하는 경로를 안내할 뿐, 스킬이 대신 계산/조회하지 않는다

## 부록 C. Skill 동작 흐름 (10단계 → 서비스 매핑)

1. 공고 읽기 & 자료 형태 확인 → 공고 데이터 확보/파싱
2. 자격조건 구조화·추출 → 공고별 자격조건 추출
3. 필요한 사용자 정보 파악 & 기존 정보 재사용 → 온보딩 + 채팅 중 추가 질문
4. 부족한 정보만 질문 → 채팅에서 AI가 질문
5. 각 필수조건 1:1 대조 (⭕/❌/⚠️) → 공고별 판정/추천 판단
6. 최종 판정 (🟢/🔴/🟡) → 개별 공고 판정 결과 + 추천 관련 판단
7. 신청기간과 자격조건 구분 → 판정 결과 출력에 반영
8. 공고자료 처리 오류 & 정정공고 처리 → 파서 에러 처리/UX 안내
9. 출력 형식 (판정 → 대조표 → 근거 → 신청 전 확인할 것 → 심사 안내) → 채팅 + 오른쪽 카드
10. 답변 전 품질검사 (내부 체크리스트) → AI 에이전트 내부 로직
